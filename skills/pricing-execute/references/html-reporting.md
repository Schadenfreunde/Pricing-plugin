# HTML reporting

By default, create a neutral, professional scrolling page with slide-like sections. Follow the user's task-specific requests for more or less detail, visuals, formatting, or report format. Choose the organization, charts, and tables for the actual question. Keep conclusions and important qualifications easy to scan; place a brief method note after the findings. Show any material reliance on unvalidated company claims beside the affected conclusion.

Use the available file tools to generate a self-contained HTML report when practical. SVG charts and HTML tables can display already computed comparisons; add controls only when they make a view easier to understand. Keep their labels and selected comparison or filter scope explicit. Controls may switch among precomputed views or reveal detail. Generated JavaScript should only handle presentation interactions, not rerun pricing calculations or change the analysis. Include only the data needed for those views; the complete source dataset need not be embedded.

For substantial reports intended for circulation, default to a static PDF print in **landscape** with readable, slide-like pages unless the user requests another format. Keep the HTML a scrolling page and choose the content and page breaks for the task; split dense material across pages rather than shrinking type or clipping it. Preserve scope, numbers, chart and table labels, material caveats, and method in the printed view. Essential information must not depend on hover or controls, and controls must not cover content. Before sharing HTML, inspect its screen view; when providing a PDF, inspect every page of the actual export. CSS rules alone do not verify a PDF.
