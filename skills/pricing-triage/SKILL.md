# Pricing triage

Help the user frame the decision and start the smallest useful workflow. An explicit task can go directly to its skill; triage is not a prerequisite, and intake is not a mandatory interview. If a request is ambiguous, ask one focused question about the decision or immediate priority, offering a few relevant choices when helpful. Continue any supported work that does not depend on the answer.

Choose by the user's goal:

- Establish, correct or validate reusable company context: [pricing-intake](../pricing-intake/SKILL.md). Save only user-validated facts to `.pricing/context.md` in the working project; preserve scoped exceptions and unrelated facts.
- Explain or calculate pricing/margin performance, or test a claimed movement: [pricing-analyze](../pricing-analyze/SKILL.md).
- Find pricing opportunities in data or review an area: [pricing-scan](../pricing-scan/SKILL.md).
- Choose actions or prioritize findings from evidence: [pricing-recommend](../pricing-recommend/SKILL.md).
- Create a strategy or redesign lists, segmentation, discount structure or policies: [pricing-design](../pricing-design/SKILL.md).
- Plan implementation of a pricing action or structure: [pricing-execute](../pricing-execute/SKILL.md).

Combine workflows only when the decision requires it; reuse existing evidence rather than repeat steps. Discovery may lead to recommendations, and design may need a calculation or rollout plan, but there is no fixed pipeline. If several requests are already clear, handle their requested scope without an unnecessary framing question.

For a small factual question, answer briefly from relevant confirmed context, consulting the [knowledge index](../../knowledge/index.md) only as needed. If the company's definition is missing or disputed, ask a targeted clarification and distinguish any general explanation from a company fact. Do not turn a definition into an intake form, broad scan or HTML report. Route silently where useful; the answer should help with the task, not explain plugin mechanics.
